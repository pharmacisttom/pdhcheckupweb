# ประเมินการใช้ระบบของผู้รับบริการบนมือถือ — 29 ตุลาคม 2569

ข้อสรุป: flow หลักเข้ากับหน้าจอและการสัมผัสของมือถือใน Chromium emulation ได้ แต่การใช้งานต่อหลังรีเฟรช/เปลี่ยนอุปกรณ์/sessionหมดอายุยังมีช่องว่างสำคัญ ไม่ใช่ผลรับรอง iOS/Safari หรืออุปกรณ์จริง

## ผลตรวจรอบนี้

- npm run test:no-otp:e2e: 4 passed (33.6s), ไม่มี skip ใช้ pdh_healthcheck_test แยกเท่านั้น ทดสอบส่งความสนใจโดยไม่OTP, ประวัติเลือก/เพิ่ม/ลบ, แบบร่างเก่า, คำถามที่ใช้ร่วมกันและกฎประเมินเดิม มี Windows EPERM ของ dev build-manifest ชั่วคราวช่วงเริ่ม แต่ชุดทดสอบจบexit0 ไม่ถือว่าไม่มี diagnostic warning
- หน้าแรก/ลงทะเบียน/รายการของฉัน × 7 widths 360/390/430/768/820/1024/1280 รวม21checks: ไม่มี horizontal overflow
- เมนูล่างที่แสดงมีพื้นที่แตะของทั้ง3ลิงก์อย่างน้อย44×44 CSSpx (ไม่ได้สรุปว่าทุกลิงก์หรือทุกcheckboxทั้งระบบผ่าน)
- เปลี่ยน th/en/zh-Hans/my/km ที่390px: document.langถูกต้อง ค่าชื่อสังเคราะห์ในฟอร์มไม่หาย ไม่มีoverflow
- Chromium touch emulation profiles iPhone13 และ Pixel7: แตะเมนูลงทะเบียน, รับทราบprivacy, แตะช่องphoneและfocusได้, แตะไปรายการของฉันได้ ทั้ง2profilesผ่าน ไม่ใช่Safari/nativekeyboard/deviceจริง การรันครั้งแรกสคริปต์ค้นข้อความไทยผิดเพราะPowerShell encoding จึงแก้encodingแล้วรันซ้ำผ่าน
- font ช่องชื่อที่360/390/430/768px =16px; ที่820/1024/1280px =13px เป็นจุดควรปรับความอ่านง่ายของtablet ไม่ได้ทดสอบnativeautozoomจริง
- phone ใช้type=tel และautocomplete=tel ชื่อ/นามสกุลมีautocomplete, วันเกิดใช้native date input
- ทดลองกรอกชื่อสังเคราะห์ในขั้นข้อมูลส่วนตัวโดยยังไม่ส่ง แล้วreload: ค่าที่พิมพ์ใหม่ไม่อยู่ (unsavedFirstStepSurvivesReload=false) ไม่ส่งข้อมูลลงทะเบียนหรือข้อมูลสุขภาพจริงในการตรวจนี้

## การเข้ากันของ flow

| ขั้นตอน | ผลประเมิน |
|---|---|
| เปิดเว็บ/QR | หน้าแรกเข้าถึงด้วยbrowser รูปภาพรักษาสัดส่วนและเปิดเต็มได้; ไม่ได้ทดสอบสแกนQRหรือin-app browserจริง |
| เลือกภาษา | มี5ภาษา ใช้ชื่อภาษาในภาษานั้นและเก็บเฉพาะlanguage preferenceในlocalStorage; คำแปลสุขภาพรอผู้เชี่ยวชาญตรวจ |
| อ่านprivacy | ต้องรับทราบก่อนเข้าฟอร์ม; ข้อความนโยบายDPO/retentionยังต้องได้รับอนุมัติ |
| กรอกตัวตน/สิทธิ | layoutมือถือช่องเดียว เมนู3รายการ ช่องเบอร์เรียกชนิดtel ไม่บังคับOTPตามโหมดปัจจุบัน |
| ประวัติ/แบบประเมิน | เลือก/เพิ่มรายการได้ คำตอบไม่หายเมื่อเปลี่ยนภาษา ลดคำถามซ้ำตามนิยามที่ปลอดภัย; ฟอร์มยังมีความยาว |
| ส่งความสนใจ | ส่งโดยไม่เลือกแพ็กเกจได้ ได้เลขติดตามที่แยกจากเลขนัด ไม่ใช่ยืนยันBooking |
| กลับมาตรวจรายการ | ใช้sessionเดิมได้; sessionหมดอายุหรือคนละอุปกรณ์ยังไม่มีidentity recoveryทางเลือกเมื่อOTPปิด |
| รับทราบราคา/วันนัด | ต้องกลับเข้าowner sessionเดิมได้ จึงรับทราบและให้เจ้าหน้าที่สร้างBookingจริงได้; recoveryเป็นจุดติดขัด |
| รับแจ้งเตือน | Notificationoutboxยังunconfigured ไม่ส่งSMS/emailจริง ผู้ใช้ต้องเปิดดูหรือเจ้าหน้าที่ติดต่อ |
| ใช้keyboard/screenreader | มีlabels/keyboardfocus/safe-areaCSS แต่ยังไม่ทดสอบคีย์บอร์ดจริง VoiceOver/TalkBack หรือnotchจริง |

## งานที่แนะนำตามลำดับ

1. ทำ secure recoveryทางเลือกเมื่อOTPปิด ให้เจ้าหน้าที่ตรวจตัวตนและคืนสิทธิ์ผ่านกระบวนการมีaudit โดยไม่เปิดจากเลขติดตาม/เบอร์เพียงอย่างเดียว และไม่ข้ามการรับทราบราคา/วันนัดของเจ้าของข้อมูล
2. เพิ่มบันทึกร่างทีละขั้นหรือautosaveฝั่งserverแบบเข้ารหัส และเตือนเมื่อจะออกจากหน้าที่ยังไม่บันทึก ปัจจุบันPOST registrationsเกิดเมื่อส่งขั้นประเมิน ไม่ใช่ทุกkeystroke ห้ามแก้ด้วยการเก็บสุขภาพในlocalStorage/URL/log
3. ทำUATอุปกรณ์จริง iPhoneSafari/AndroidChrome/iPad/Androidtablet ทั้งสองแนว รวมเปิดคีย์บอร์ด สลับแอป browserback refresh เน็ตขาด/ช้า และscreenreader พร้อมปรับฟอนต์tablet13pxและตรวจtouch targetsทุกชนิด
4. แก้ข้อความหน้าแรกที่ยังกล่าวถึงยืนยันเบอร์โทรให้ตรงกับOTPdisabled และกำหนดวิธีเจ้าหน้าที่ติดต่อกลับ/แจ้งเปลี่ยนแปลงนัดที่ทำได้จริงในงบปัจจุบัน
