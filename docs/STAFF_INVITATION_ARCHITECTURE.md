# Existing architecture and implementation plan — 2026-10-29

Baseline main 3c0c301. Next16.4.2/React19/TypeScript/Prisma6.19/MySQL8. Inspected AGENTS, local Next route/client guides, schema/migrations, security.ts, staff-users.ts, enrollment.ts, api.ts, staff UI and existing staff integration/E2E fixtures before application edits.

Existing: User string-role with permission map (manager/superadmin users:manage; only superadmin manages superadmin). bcrypt12, 14-character passwords (72-byte bcrypt limit), HttpOnly staged sessions (password/mfa/full), encrypted TOTP with otpauth, origin checks, persistent rate limits, transactional audit. UserInvitation already stores only SHA256(token), userId, creator, expiry and consumedAt. Invitation-only accounts are pre-provisioned and cannot activate an already-active identity. /auth/activate uses a fragment token and clears it. Privileged actions require current administrator password + TOTP. No email delivery or password-reset/recovery-code storage exists. Notification patient outbox is unrelated and must not be reused for staff credentials.

Plan BEFORE implementation: additive User department/position; extend UserInvitation lifecycle/delivery metadata and recipient note; new StaffPasswordReset (token hash, expiry30min, consumedAt), MfaRecoveryCode (user+hash+usedAt). No old data deletion; do not touch real users. Existing invitations remain consumable using consumedAt/revokedAt/expiry as authority, with effective lifecycle derived for historical records.

Recovery-code proposal BEFORE development: create 10 independent 128-bit random codes when TOTP enrollment completes; store only hashes; display once in memory. Login requires password AND valid TOTP or atomically consumed recovery code. Password email reset never removes MFA. Admin MFA reset requires another authenticated manager/superadmin, reason and fresh password/TOTP, revokes sessions and codes, then requires password change and MFA enrollment again. Tests must cover reuse/races, wrong user, secret-free API/history/audit, and reset retaining MFA.

Email: shared typed adapter disabled by default; SMTP TLS and Resend HTTPS; future providers implement same send contract. Immediate token delivery from memory after DB commit, no plaintext/encrypted token in DB/outbox. Persist safe sent/disabled/failed status and generic audited failure only. SMTP/provider credentials and sender verification external. Expired invitation notices use a bounded scheduled script without secrets.

URL decision: preserve /auth/activate#token and expose /invite#token and /reset-password#token aliases. Do NOT emit /invite/token or reset-password/token: reverse proxies can log the first request before app strips it. Fragment is removed immediately before POST verification; no third-party tracking. No production action or real mail until configured and operator verifies sender.

Sequence: schema/migration -> adapter/templates -> invitation lifecycle/filters -> password reset -> recovery codes -> existing UI extensions -> isolated tests -> docs/security/deploy/rollback -> feature commit/PR. Existing uncommitted mobile audit artifacts remain untouched and outside feature commit. Staging and real email acceptance cannot be claimed without credentials/authorized access.

Implemented: two additive migrations; legacy consumedAt ambiguity is preserved. Expiry worker has an explicit service audit actor/correlation without HTTP headers context. Public reset requests are anonymous audit events; email delivery is a service actor. Deployment runner clears inherited email configuration before protected env loading.
