# Health Chat architecture audit and plan — 2026-10-30

Base: staff feature e8a0ad8 (draft PR1), itself based on main3c0c301. Existing Next16.4.2/React19/TypeScript/Prisma6/MySQL8, catch-all API with measured-body/origin guards, staged HttpOnly sessions, MFA, role permission map, AES-GCM encryption, audit with worker correlation, public mobile nav, systemd/Nginx release scripts. No chat, KB or AI delivery exists in baseline. Existing staff department text is NOT authorization; explicit ChatAgent membership is required.

Plan before code: new additive ChatDepartment/ChatAgent/ChatConversation/ChatMessage/ChatAssignment/ChatFeedback/ChatKnowledge/ChatKnowledgeVersion/ChatKnowledgeChunk/ChatKnowledgeCitation/ChatAIUsage/ChatConfiguration tables; reuse User/Session and existing Audit. Public messages/notes/feedback encrypted. Knowledge plaintext is deliberately public approved material; private draft content is never sent to provider. Content versioning and independent clinical approval; publication withdrawal rechecks SQL immediately, no answer cache.

Operational baseline: chat and external AI disabled by default. Public conversations require an approved notice version and retention period, existing session and explicit acknowledgement. Initially only Health Check and General Information departments are enabled. Staff membership managed by authorized administrator, no implicit cross-department access. Polling with sequence cursors and UUID idempotency, row-locked assignment/takeover, notes filtered from public responses, no new public port/Redis/worker required for live chat. Expiry/retention workers are explicit operator commands, not auto-installed services.

Conservative RAG: local keyword/FAQ retrieval first, published/public/unexpired material only. Insufficient/ambiguous/sensitive/medical/emergency input hands off rather than guessing. Explicit emergency message follows the hospital-provided prompt (1669; do not wait for chat), not an autonomous diagnosis. Answers are exact approved extracts with version citations; no confidence percentages. Price text requires a current approved catalogue binding or handoff; no image-derived values.

External provider adapter (OpenAI Responses/compatible API) is opt-in behind external-processing approval and budget configuration. Raw user messages/history/health data are NEVER sent; only already-public approved candidate records and approved matched keyword labels. Provider may select an allowed evidence ID; client-generated prose is not trusted or used as an answer. Validate selection and recheck publication/kill switch/human mode after provider completes. Provider outage falls back locally or hands off. Token/request/cost reservations use DB locks; no invented provider prices/costs. Semantic/vector search remains a pluggable extension, not an added database.

Import plan: text-only extraction of bounded TXT/PDF/DOCX into draft, no automatic approval or model instructions from files. File signatures, size/output/page/ZIP bounds and isolated processing required. Original files not publicly served. Clinical self-approval forbidden. No conversation-to-FAQ automation; staff must redact and author a new draft.

Phases:1 foundation+inbox;2 KB/approval/import;3 extractive provider/RAG;4 reporting/settings/retention; then isolated security/E2E/build review and staging handoff. No real patients/test data, provider send, production changes or deployment without approval. Actual VPS state/SMTP/AI credentials not available; no remote acceptance claimed.

Implementation update 2026-10-30: public modal widget, consent, inbox, settings, policy approval, membership, KB forms/import workflow, source page and aggregate reports with CSV/XLSX added. See TEST_PLAN and OPERATIONS for actual tested scope and remaining acceptance. Optional provider is extractive evidence selection only. Fulltext index exists but bounded keyword retrieval is current implementation. No production enablement.
